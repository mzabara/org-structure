# API — решения по дизайну внешнего API

Контракт — `docs/openapi.yaml`. Здесь объяснено, ПОЧЕМУ он такой, чтобы агент и люди не «улучшали» его по своему вкусу.

## Принципы
1. **Только чтение.** Потребители интеграции пока неизвестны. Чтение безопасно, запись добавим, когда появятся сведения.
2. **Версия в пути** (`/api/v1`). Добавлять поля можно, удалять и переименовывать — только в v2.
3. **Универсальные формы данных.** Короткий объект `EmployeeSummary` для списков и ссылок, полный `Employee` для карточки,
   вложенные деревья для визуализации. Внешняя система может взять любую форму.
4. **Деревья отдаются готовыми** (`/departments/tree`, `/employees/tree`): клиенту не нужно собирать их из плоских списков.
5. **Матричные связи не ломают дерево.** Дерево людей строится по LINE, а DOTTED отдаются отдельным полем.
6. **Единый формат ошибок** — `application/problem+json` (RFC 9457).
7. **Пагинация** только там, где список может быть большим (сотрудники). Деревья и цепочки возвращаются целиком, но с ограничением `depth`.

## Аутентификация
- Заголовок `X-API-Key: <ключ>`.
- Ключи задаются в конфигурации `app.security.api-keys` (список). Пустой список или профиль `dev` — проверка отключена.
- Ключи сравниваются в постоянное время и никогда не пишутся в лог.
- Для UI в dev-режиме ключ не нужен. В реальной эксплуатации потребителю выдаётся персональный ключ.
- Когда станет известна система интеграции, возможен переход на OAuth2/JWT — это изменит только схему безопасности.

## Заготовки на будущее (НЕ реализуем сейчас)
- Вебхуки об изменениях оргструктуры.
- Запись (POST/PATCH) и роли доступа.
- Эндпоинт delta-синхронизации (`?updatedSince=`), если потребителю понадобится инкрементальная загрузка.
- Ограничение частоты запросов (rate limit).

## Коды ответов
| Код | Когда |
|---|---|
| 200 | успех |
| 400 | неверные параметры (пустой `q`, `size` > 100 и т. п.) |
| 401 | нет/неверный API-ключ |
| 404 | объект не найден |
| 500 | непредвиденная ошибка (тело — problem+json без внутренних деталей) |

## Правила для агента
- Не добавляй эндпоинты и поля «на всякий случай». Если контракт не покрывает задачу UI — сообщи человеку.
- Любое изменение контракта — только по просьбе человека, затем обновляются backend, frontend-типы и тесты.
