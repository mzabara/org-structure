# BRIEF — Оргструктура компании

## Цель
Наглядно показать, как устроена компания: какие есть подразделения, кто в них работает,
кто кому подчиняется (включая матричное подчинение) и за что отвечает каждый сотрудник.
Дать другим системам компании доступ к этим данным через внешний API.

## Пользователи
- **HR и руководители** — смотрят структуру, ищут людей и отделы.
- **Новые сотрудники** — понимают, к кому идти с вопросом.
- **Внешние системы** (интеграции) — читают данные через REST API. Конкретные потребители пока неизвестны,
  поэтому API проектируется универсальным и только на чтение.

## Что должно быть в MVP
1. **Дерево подразделений** (отдельный экран/вкладка): иерархия отделов, у каждого узла — число сотрудников.
2. **Дерево сотрудников** (отдельный экран/вкладка): иерархия по линейному подчинению;
   пунктирные (матричные) связи показываются отдельно.
3. **Карточка отдела**: название, описание, руководитель, родительский и дочерние отделы, список сотрудников.
4. **Карточка сотрудника**: ФИО, должность, контакты, ОТДЕЛ (ссылка на карточку отдела),
   линейный руководитель, матричные руководители, прямые подчинённые,
   список «Задачи» (что делает) и «Зоны ответственности» (за что отвечает).
5. **Сворачивание/разворачивание** веток в обоих деревьях.
6. **Поиск** по ФИО/должности/названию отдела; результат раскрывает путь до найденного узла.
7. **Внешний REST API** `/api/v1` (только чтение) по контракту `docs/openapi.yaml`, с аутентификацией по API-ключу.

## Nice-to-have (только если MVP принят)
- Фильтр дерева сотрудников по отделу, цветовая кодировка отделов.
- Экспорт дерева в PNG/SVG.
- Режим «показать цепочку подчинения от сотрудника до руководителя».
- Вебхуки об изменениях (когда появятся сведения об интеграции).

## Вне рамок (не делаем)
- Редактирование данных через UI и запись через API.
- Авторизация пользователей UI (вход по логину), роли.
- Реальные персональные данные.
- Импорт из внешних систем.

## Критерии успеха
- Деревья читаемы на 30+ сотрудниках и 13 отделах, интерфейс не «тормозит».
- Любой пункт MVP проверяется по `docs/ACCEPTANCE.md`.
- Внешний API соответствует `docs/openapi.yaml`: клиент можно сгенерировать по контракту.
- Код понятен человеку, который его не писал (см. `docs/CODE-STYLE.md`).

## Ранее открытые вопросы — решения приняты
- Матричные связи на дереве линиями не рисуем: показываем в карточке сотрудника
  и подсвечиваем матричных руководителей на дереве при выборе. См. `docs/UI.md`, «Дерево сотрудников».
- В карточке отдела список сотрудников — с переключателем «Включая вложенные подразделения».
  См. `docs/UI.md`, «Карточка отдела».

Новые вопросы, найденные на этапе спецификации (например, `spec_critic`), дописываем сюда
и решаем до заморозки контракта.
