# Правила проекта «Оргструктура» (для Codex)

Приложение показывает оргструктуру компании: дерево подразделений, дерево людей
(с матричным подчинением), карточки сотрудников и отделов, а также внешний
REST API для интеграции. Все данные в проекте синтетические.

## Прочитай перед работой
1. `docs/BRIEF.md` — что делаем и что не делаем.
2. `docs/DOMAIN.md` — термины и правила предметной области.
3. `docs/PLAN.md` — текущий план; работай только над назначенным пунктом.
4. Если задача касается API — `docs/openapi.yaml` (это контракт, источник истины).
5. Если задача касается БД — `docs/DB.md`.
6. Стиль кода — `docs/CODE-STYLE.md`.

## Стек
- Frontend: Angular 22 (`frontend/`), правила — `frontend/AGENTS.md`.
- Backend: Kotlin + Spring Boot (`backend/`), правила — `backend/AGENTS.md`.
- БД: PostgreSQL, схема меняется только миграциями Flyway.
- Запуск БД: `docker compose up -d db`.

## Как работать
- Сначала план, потом код. Перед правками перечисли файлы, которые изменишь, и дождись «ок».
- Один пункт плана за раз. Делай вертикальный срез: БД → API → UI → проверка.
- Не трогай файлы, не относящиеся к задаче. Новые зависимости — только по согласованию.
- `docs/openapi.yaml` меняй только по явной просьбе человека. Нашёл расхождение — сообщи, не «чини молча».
- Если требования неясны — задай один уточняющий вопрос, а не выдумывай.
- Не используй реальные персональные данные. Только синтетика из seed-миграции.

## Читаемость кода (обязательно)
- Комментарии и KDoc/TSDoc — на русском. Идентификаторы — на английском.
- Комментарий объясняет «почему», а не повторяет «что». Подробности — `docs/CODE-STYLE.md`.
- Каждый публичный класс, сервис и компонент имеет краткий комментарий «зачем он нужен».
- Строки интерфейса — на русском.

## Проверка и завершение задачи
Перед тем как сказать «готово»: запусти проверки, сверяй результат с
`docs/ACCEPTANCE.md`, отмечай пункт в `docs/PLAN.md` и предложи сообщение
коммита. Коммитит человек, если не сказано иное.
